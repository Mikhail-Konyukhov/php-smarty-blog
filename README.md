# Блог на PHP, Smarty и MySQL

Проект представляет собой блог с категориями и статьями, разработанный по тестовому заданию. Используемые технологии: PHP 8.4, Smarty 5, MySQL 8.4. Фреймворки не используются.

## Запуск

Для запуска требуется Docker с Compose v2. Запуск выполняется скриптом `./start.sh` в Linux или `start.bat` в Windows (двойным щелчком). Скрипт собирает и запускает контейнеры, заполняет базу данных сидером, проверяет доступность сайта и открывает его в браузере.

Запуск вручную выполняется командами:

```bash
docker compose up -d --build
docker compose exec app php bin/seed.php
```

Сидер создаёт 8 категорий и 300 статей. При повторном запуске сидера или скрипта данные создаются заново.

Сайт доступен по адресу http://localhost:8080. Если порт 8080 занят, Docker выбирает другой свободный порт из диапазона 8080–8099. Скрипт выводит фактический адрес и открывает его, после ручного запуска адрес показывает команда `docker compose port app 80`. Фиксированный порт задаётся переменной окружения `APP_PORT`: `APP_PORT=8090 docker compose up -d`, скрипты запуска также её используют. Журнал ошибок выводится командой `docker compose logs app`.

CSS собирается из файлов `scss/` при запуске. Для пересборки после каждого изменения SCSS используется команда `docker compose run --rm assets npm run watch`.

MySQL выполняет файлы `database/*.sql` только при первом запуске, на пустом томе. После изменения схемы том необходимо пересоздать, данные при этом удаляются:

```bash
docker compose down -v && docker compose up -d
```

Каталог `vendor/` размещён в томе Docker, а не в каталоге проекта. На Docker Desktop запись в каталог проекта выполняется в десятки раз медленнее, и `composer install` не укладывался в тайм-аут. Вследствие этого каталог `vendor/` на хосте пуст, и IDE не распознаёт классы Smarty и PHPUnit. Для получения подсказок IDE допускается выполнить `composer install` на хосте, для этого требуется PHP 8.4.

## Тесты

```bash
docker compose exec app vendor/bin/phpunit
```

Модульные тесты проверяют класс `Pagination` без обращения к базе данных. Интеграционные тесты проверяют все SQL-запросы обоих репозиториев на отдельной базе `blog_test`, каждый тест выполняется в транзакции с последующим откатом. Контроллер, `index.php` и шаблоны автотестами не покрыты, их работа проверена в браузере.

Тесты не изменяют базу данных сайта: `phpunit.xml` принудительно устанавливает `DB_NAME=blog_test`, а `DatabaseTestCase` завершается с ошибкой при подключении к другой базе.

## Структура

```
bin/         сидер и запросы для замера
database/    схема и база для тестов, MySQL выполняет их при первом запуске
docker/      Dockerfile образа PHP с Apache
public/      корень сайта: index.php, картинки, собранный CSS
scss/        стили
src/         контроллер, репозитории, пагинация, сортировка
templates/   шаблоны Smarty
tests/       Unit: пагинация, Integration: SQL репозиториев
```

## Решения

- Маршрутизация. Отдельный класс роутера не используется: `public/index.php` сравнивает путь с `/` и проверяет его двумя выражениями `preg_match`. Для трёх страниц, обрабатывающих только GET-запросы, такой класс содержал бы лишь цикл по регулярным выражениям. Его введение целесообразно при появлении форм, ответа 405 и десятка маршрутов.
- Репозитории. Репозиторий служит местом размещения SQL-запросов, а не обёрткой над таблицей. Каждому запросу соответствует один метод с необходимыми JOIN. Репозитории не вызывают друг друга, данные для страницы собирает контроллер.
- Главная страница. Данные формируются одним запросом: функция `ROW_NUMBER()` нумерует статьи внутри каждой категории по дате, запрос отбирает первые три. Отдельный запрос для каждой категории привёл бы к N+1 запросам. Категории без статей исключаются за счёт JOIN.
- Похожие статьи. Отбираются статьи с наибольшим числом общих категорий, при равном числе приоритет имеют более новые. Если найдено менее трёх статей, выводятся все найденные.
- Учёт просмотров. При каждом показе выполняется `UPDATE articles SET views = views + 1`. Запрос атомарен, поэтому параллельные просмотры не теряются. Защита от повторных просмотров и ботов не реализована. При высокой нагрузке рекомендуется вести счётчик в Redis с периодическим сбросом в MySQL.
- Индексы. Созданы только первичные ключи и индексы для внешних ключей: на 300 статьях разница в производительности не поддаётся измерению. Замедление на 200 000 статей и способы его устранения описаны в разделе «Замер на 200 000 статей».
- Текст статьи. Хранится как обычный текст, абзацы разделяются пустой строкой и отображаются с помощью свойства CSS `white-space: pre-line`. Автоэкранирование Smarty нигде не отключено. При появлении редактора статей возможен переход на HTML: очистка текста через HTML Purifier при сохранении и вывод с `nofilter`.
- Сортировка. Задаётся параметром `?sort=date|date-asc|views|views-asc`, по умолчанию статьи упорядочены от новых к старым. Повторное нажатие на ссылку активной сортировки меняет её направление. Колонку и направление в `ORDER BY` невозможно передать параметром подготовленного запроса, поэтому соответствующий фрагмент SQL формируется только перечислением `ArticleSort`. Неизвестное значение приводится к сортировке по дате.
- Пагинация. На странице категории выводится 9 статей. Отображаются номера первой и последней страниц и по две страницы вокруг текущей, пропущенные номера заменяются знаком «…». Пропуск одной страницы заменяется её номером: «1 2 3», а не «1 … 3». Логика реализована в методе `Pagination::links()` и покрыта тестами.
- Обработка ошибок. Предупреждения PHP и обращения к неизвестным переменным шаблона преобразуются в исключения. В противном случае некорректная страница отдавалась бы с кодом 200 и пропусками в содержимом. Для ненайденной страницы возвращается код 404, при любом другом исключении выводится страница 500, подробности записываются в журнал.

## Замер на 200 000 статей

Раздел показывает, какие запросы замедлятся при росте объёма данных и как это устранить. На 300 статьях все запросы выполняются не более чем за 20 мс, и узкие места не проявляются.

```bash
docker compose exec app php bin/seed.php 200000
docker compose exec -T db mysql -ublog -pblog -rN blog < bin/explain.sql
```

Заполнение базы занимает около 10 минут, прогон `bin/explain.sql` около 3,5 минут. Скрипт выполняет через `EXPLAIN ANALYZE` четыре наиболее ресурсоёмких запроса в исходном и исправленном виде. Для исправленных запросов создаётся временная копия таблицы `article_category`, по завершении она удаляется. Условия замера: Docker Desktop (WSL2), MySQL 8.4 с настройками по умолчанию, медиана трёх прогонов.

| Запрос | 300 статей | 200 000 статей | 200 000, с исправлением |
|---|---|---|---|
| Главная | 19 мс | 25,5 с | 0,69 с |
| Первая страница категории | 1,6 мс | 10,2 с | 27 мс |
| Последняя страница категории, 7444-я | 1,4 мс | 12,2 с | 120 мс |
| Похожие статьи | 2,7 мс | 108 с | 0,71 с |

Причина замедления: все четыре запроса читают таблицу статей полностью или почти полностью и сортируют все найденные строки.

Исправление: копия столбца `published_at` в таблице `article_category` и индекс `(category_id, published_at)`. По этому индексу запросы получают статьи категории уже упорядоченными по дате и читают из `articles` только нужные строки. Главная страница и похожие статьи после исправления выполняются около 0,7 с. Их содержимое меняется только при публикации статьи, поэтому для них дополнительно рекомендуется кэширование.

Исправления в код не внесены: первым критерием задания является простота, а копию даты пришлось бы обновлять вместе со статьёй.

## Не реализовано

Административная панель, вход в систему, комментарии, поиск и загрузка изображений не реализованы, так как не предусмотрены заданием. Статьи и категории создаются сидером.

## Использование ИИ

Приложение разработано с использованием Claude Code. Архитектура и технические решения приняты автором, варианты решений оценивались с помощью ИИ. До написания кода выполнено проектирование в три уровня: стек и данные, классы и методы, сигнатуры и SQL. Код написан ИИ по утверждённому плану поэтапно, коммит за коммитом, каждый коммит разобран. Запуск тестов и ревью кода также выполнялись ИИ.
